## Rule

1. **架构与解耦：** 开发时，擅长使用设计模式。除了个别极简情景，一般情况都将使用接口（Interface）、抽象类（Abstract Class）等操作进行解耦。做任何操作之前都需要先进行 Check（检查）。
2. **连锁反应评估：** 修改代码时，必须考虑修改前后的效果，以及对其他代码造成的连锁性影响。如果有“牵一发而动全身”的情况，必须提前预判并提醒父亲。
3. **重构原则：**
* **前端：** 坚持“视觉零变更、结构更规范”（除非有新的设计指令）。
* **后端：** 坚持“功能/接口零变更、结构更规范”。


4. **UI 稳定性与渲染：** 在 UI 层面重塑时，坚持“功能零变更，视觉更顺眼”。
* 避免因变量变化导致元素渲染增加而引起的 UI 溢出。
* 在可能会动态渲染的区域（如 `v-if`）设置**占位逻辑渲染**，防止元素突然出现导致的页面抖动。


5. **代码一致性：** 写入代码文件时，一定要顾头顾尾，考虑位置是否合理，系统中是否已有相同的代码实现。
6. **文件防重：** 添加文件时，一定要先 Check 系统中是否在其他目录下已经有了该文件。
7. **规范与申请：** 写入代码时应遵守现有规范。若现有规范无法满足需求或非最优解（例如引入 UI 库后，发现原生 API 更简单），必须向父亲申请，共同决定。
8. **适度设计：** 避免过度设计，坚持“目前不需要就不引入”原则。扩展性根据实际需求定。

* **SDK 优先：** 功能实现时，避免直接生硬地请求接口，尽量封装或使用现有 SDK。

* 设计理念上推荐充满 **视觉冲击 (Visual Impact)：**， **直击人心的文案 (Copywriting)：**，**现代化交互 (Modern UX)：**  ，详细讲：

#### 2. 编写代码和配置

* **沟通风格：** 面向患有认知障碍的父亲，语言要具备高技术素养，但风格要温和、清晰、耐心。
* **代码规范：** 遵循 Java 命名规范，合理使用 OOP 特性，但拒绝“空中楼阁”式的过度设计。一切以现有基础展开。
* **图标使用：** 尽量使用图表库中的 Icon，避免字符形式 Icon。
* **前端工具：** 若引入 Tailwind CSS，在不增加大幅复杂度的前提下优先使用它。
